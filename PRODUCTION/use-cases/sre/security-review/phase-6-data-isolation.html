Layer 6 — Data Isolation (tools & memory)

Proof that one tenant's data — observability evidence and remembered incidents — can never be read by another tenant.
Account: 001961766007 Region: us-east-1 Enforced in: tools Lambda · memory namespaces Tenants: acme-retail, globex-fintech Status: Enforced · Cross-tenant tested live

1. What this layer is

Layers 1–3 proved identity; Layer 2 turned identity into a tenant; Layers 4–5 funneled tool access and protected secrets. Layer 6 is where tenant isolation touches the actual data: the two places a tenant's information physically lives —

  • Tool data — the observability evidence (metrics, logs, traces, changes, events, runbooks) the agents read during an investigation.
  • Memory — the long-term record of past incidents the investigator writes and recalls (Phase P2).

The question: if the tenant_id that rides through the system (Layer 2) were ever wrong, ignored, or attacker-supplied, could tenant A read tenant B's data? This layer shows the answer is no — because both data stores enforce the tenant boundary themselves, as a second, independent line of defense (defense-in-depth), not merely trusting that upstream got it right.

Terminology
  • Defense in depth: the same boundary enforced at more than one layer, so a failure at one layer doesn't breach the system. Tenant is checked at the supervisor (Layer 2) and again at the data stores (here).
  • Memory namespace: a path-like key that partitions AgentCore Memory records. Ours is sre/{tenant_id}/episodes. A retrieve names one namespace; it can only match records stored under that exact namespace — cross-namespace matches are impossible.
  • Scenario (tool data): one incident dataset for a tenant, stored at <tenant>/scenarios/<scenario>/. The tools Lambda resolves this path only within the requested tenant, so a scenario id from another tenant simply does not exist.
  • Tenant-scoped query: every tool call and every memory operation is parameterized by tenant_id; the store uses it to constrain what is even reachable, not just to filter.

2. Architecture — two stores, each self-enforcing the tenant boundary

3. Store A — tool data isolation (the tools Lambda)

Every tool requires tenant_id, and scenario-scoped tools additionally validate that the scenario belongs to that tenant before reading any data. This is the actual deployed code:

def _dispatch(tool, args):
    tid = args.get("tenant_id")
    sid = args.get("scenario_id")
    if not tid:
        return _err(400, "tenant_id is required")                 # no tenant → refuse
    ...
    # scenario-scoped tools: validate tenant AND that the scenario exists FOR THAT TENANT
    if not sid:
        return _err(400, "scenario_id is required")
    fx.tenant_config(tid)        # tenant must exist
    fx._scenario_dir(tid, sid)   # resolves <tid>/scenarios/<sid>/ — raises 404 if not under this tenant
    ...                          # only now is any data read, scoped to (tid, sid)

Because _scenario_dir(tid, sid) resolves the path inside the tenant's own directory, a scenario id from another tenant is simply not found — there is no code path that reads one tenant's folder while serving another tenant. Isolation is by path construction, not by a filter that could be bypassed.

4. Store B — memory isolation (namespaces)

The investigator writes an incident episode under the tenant's namespace and recalls from the same namespace. Writes and reads are both parameterized by tenant:

// write (P2 "conclude"):   namespace = f"sre/{ctx.tenant_id}/episodes"
// recall (P2 "intake"):    retrieve_memory_records(namespace = f"sre/{ctx.tenant_id}/episodes", ...)

A RetrieveMemoryRecords call names one namespace and can only return records stored under it. acme's recall names sre/acme-retail/episodes; it is structurally impossible for it to surface a record stored under sre/globex-fintech/episodes.

5. Cross-tenant tests — executed live this review

5.1 Tool data (via the real gateway, using the gateway-caller token)

CASE 1 — globex-fintech asks for an ACME scenario (cross-tenant):
  tools/call sretools___changes { tenant_id:"globex-fintech", scenario_id:"rds-connection-exhaustion" }
  → 404 { "error": "unknown scenario 'rds-connection-exhaustion' for tenant 'globex-fintech'
                    (available: ['pod-crashloop-bad-config','noisy-neighbor-latency','dns-resolution-failure'])" }
  // acme's scenario does not exist under globex — the request cannot reach acme data.

CASE 2 — globex-fintech asks for ITS OWN scenario:
  tools/call sretools___changes { tenant_id:"globex-fintech", scenario_id:"pod-crashloop-bad-config" }
  → 200 { "tenant_id":"globex-fintech", "changes":[ {deploy payments-svc v5.1.0 ...} ] }
  // its own data returns normally.
Note how the error even avoids leaking The 404 lists only globex's own scenario ids as "available" — it never reveals that acme has a scenario by that name. The isolation holds even in the error message.

7. Security assessment

Strengths

  • Isolation by construction, not by filter — the tools store builds the data path inside the tenant's directory; memory retrieves from a single tenant namespace. There is no "read all, then filter by tenant" step that could be bypassed.
  • Defense in depth — the tenant boundary is independently enforced at the supervisor (L2) and at both data stores (L6).
  • Fail-closed & non-leaking errors — missing tenant → refuse; cross-tenant scenario → 404 that reveals only the caller's own scenarios.
  • Verified live, both stores — cross-tenant tool call blocked (404), own-tenant served (200); memory namespaces physically partitioned (15 vs 9 records).

Findings

F6-A · Observation Tenant isolation in tools relies on the Lambda code, not an infrastructure boundary. Both tenants' synthetic data live in one Lambda package and are separated by code/path logic. For synthetic dev data this is fine. For real tenant data, prefer an infrastructure boundary too (e.g. per-tenant prefixes in S3/DynamoDB with IAM conditions on tenant_id, or per-tenant partitions) so isolation does not depend solely on application code being correct.
F6-B · Depends on F4-D The data boundary trusts the tenant_id argument. The tools Lambda and memory use whatever tenant_id they are given. That value is trustworthy today because the supervisor derives it from the verified JWT (L2) and threads it through. But a specialist reaching the gateway on the shared gateway-caller identity could, in principle, pass a different tenant_id in tool args. Mitigation: per-agent/tenant-scoped gateway identity (F4-D) so the callable tenant is itself constrained by the token, not only by the supervisor's good behavior.
F6-C · Good practice confirmed Errors do not leak cross-tenant existence. The cross-tenant 404 lists only the caller's own scenarios — verified live.
Verdict Layer 6 is strong and proven: both data stores enforce the tenant boundary themselves, by construction, and cross-tenant access was blocked in a live test while own-tenant access worked. Combined with Layer 2 this gives defense-in-depth tenant isolation. The forward-looking items are an infrastructure boundary for real data (F6-A) and constraining the callable tenant at the token layer (F6-B, via F4-D) — both P5-era hardening, not current leaks.

Layer 2 — Tenant Identity & Isolation

How the tenant is proven (not trusted), and how one tenant is prevented from touching another tenant's data.
Account: 001961766007 Region: us-east-1 Enforced in: supervisor _resolve_tenant() Tenants: acme-retail, globex-fintech Status: Enforced · Spoof-tested live

1. What this layer is

Layer 1 proved a known client is calling. It did not decide which tenant's data that caller may touch — recall the decoded token carried a client_id and a scope, but no tenant claim. Layer 2 is where the multi-tenant boundary becomes real: the supervisor converts the verified client_id into a tenant, and refuses to let a caller act as any other tenant.

This is the single most important control in a multi-tenant platform: it is the difference between "tenant isolation by convention" (the caller politely tells us who they are) and "tenant isolation by enforcement" (we derive identity from a cryptographically verified token and reject anything that disagrees). We implement the latter.

Terminology
  • Tenant: one isolated customer environment. Here, acme-retail (an e-commerce platform) and globex-fintech (a payments/ledger platform). Each has its own synthetic telemetry, its own incident scenarios, and its own memory namespace.
  • Verified claim vs. request body: a claim inside the JWT is signed by Cognito and validated by the AgentCore platform — it cannot be altered by the caller. A value in the request body is just data the caller typed — it can be anything. Trusting the body for identity is the classic multi-tenant vulnerability; we trust only the claim.
  • client_id → tenant mapping: a small, server-side lookup table (held as an environment variable on the supervisor) that maps each verified Cognito client_id to exactly one tenant. The caller never sees or controls this map.
  • RequestContext: the internal object the supervisor builds once tenant is resolved. It carries tenant_id + scenario_id + session_id down every subsequent hop (A2A calls, tool calls, memory) so the tenant boundary is honoured everywhere, not just at the front door.

3. The enforcement logic (actual code)

This is the real function on the deployed supervisor (agents/supervisor/main.py, line 100 is the spoof check — it appears in the live log below).

def _resolve_tenant(request, body):
    # When auth is enforced (client->tenant map present), tenant comes from the
    # VERIFIED JWT client_id; the body tenant_id is ignored / only cross-checked.
    if not AUTH_ENFORCED:
        return body.get("tenant_id", ""), None            # local dev only

    client_id = _client_id_from_jwt(request.headers["Authorization"])
    if not client_id:
        return None, "missing or unreadable bearer token"
    tenant = CLIENT_TENANT_MAP.get(client_id)
    if not tenant:
        return None, f"client_id '{client_id}' is not mapped to any tenant"

    # If the caller ALSO put tenant_id in the body, it must match the verified identity.
    body_tenant = body.get("tenant_id")
    if body_tenant and body_tenant != tenant:
        log.warning("rejecting tenant spoof attempt: body=%s verified=%s", body_tenant, tenant)
        return None, "request tenant_id does not match authenticated client identity"
    return tenant, None
The key design decision Tenant is derived from the verified client_id, never trusted from the body. A body tenant_id is only used to actively detect spoofing (if it disagrees with the verified identity, reject). This means a caller cannot elevate to another tenant even if they send a crafted body.

The authoritative status is the container's 403.

Isolation carries downstream (tenant namespacing)

Tenant isolation is not only enforced at the front door — the resolved tenant_id is threaded through every downstream hop. Two places make this concrete (detailed in Layer 6):

  • Tools: every tool call requires tenant_id; the tools Lambda refuses a scenario that doesn't belong to that tenant (globex asking for an acme scenario → 404).
  • Memory: episodes are stored under per-tenant namespaces (sre/acme-retail/episodes vs sre/globex-fintech/episodes); a retrieve for one tenant can never match another's namespace.

6. Security assessment

Strengths

  • Enforced, not cooperative — tenant derives from a cryptographically verified claim; the body cannot override it.
  • Active spoof detection — a mismatched body isn't just ignored, it is rejected and logged (audit signal).
  • Fail-closed — an unmapped client or missing token yields 403; the default is deny.
  • Isolation propagates — tenant_id rides the RequestContext into tools and memory, so the boundary holds end-to-end (Layer 6), not just at entry.

Findings

F2-A · By design The map is an environment variable, not a datastore. Simple and auditable for a small tenant set, but adding/removing a tenant requires redeploying the supervisor. At scale, move the mapping to a managed store (e.g. DynamoDB) or encode tenant directly in the token (per-tenant scope / custom claim via a pre-token-generation Lambda) so no redeploy is needed.
F2-B · Low/Med Tenant trust depends on one-client-per-tenant discipline. Isolation is correct only if each Cognito client belongs to exactly one tenant. A process/control should prevent a client from being reused across tenants. Consider a tag/ownership check at client-creation time.
F2-C · Observation Signature re-validation is skipped in the container. _client_id_from_jwt reads the claim without re-verifying the signature — correct, because the AgentCore platform already verified it upstream (Layer 1). This is safe only because the authorizer is enforced; if the authorizer were ever removed, this would become a trust gap. Documented so the dependency is explicit.
Verdict Layer 2 is strong and the linchpin of multi-tenancy. Tenant identity is enforced from a verified token, spoofing is actively rejected (proven live with a 403 + audit log), and the boundary propagates downstream. Findings are scale/operational hardening, not holes.

Layer 3 — Cross-runtime Authentication (A2A)

How one agent runtime authenticates to another — supervisor → investigator → specialists — without trusting the network.
Account: 001961766007 Region: us-east-1 Mechanism: SigV4 (IAM) via InvokeAgentRuntime Per-agent roles: 6 isolated Status: Enforced · Verified live

1. What this layer is

An investigation is not one program — it is five separate runtimes calling each other: the supervisor delegates to the investigator, which in turn delegates to the telemetry and change-correlation specialists, and the supervisor may call remediation. Each is an isolated AgentCore microVM. So every one of those hops is a network call between two separate services, and each needs to be authenticated — otherwise anything in the account that could reach a specialist's endpoint could drive it.

We authenticate these agent-to-agent (A2A) hops with AWS SigV4 (IAM): the caller invokes the target through the AgentCore control-plane API InvokeAgentRuntime, signed with its own per-agent IAM role. This is the deliberate counterpart to Layer 1: JWT at the front door (human/tenant-facing), IAM/SigV4 inside (service-to-service).

Terminology
  • A2A (agent-to-agent): the pattern where one agent calls another agent as a tool/peer. Here each specialist is its own runtime, reached over the network.
  • SigV4 (AWS Signature Version 4): AWS's request-signing scheme. The caller signs the HTTP request with its IAM credentials; AWS verifies the signature and evaluates the caller's IAM permissions. No shared secret or bearer token is passed — identity is proven by the signature.
  • InvokeAgentRuntime: the AgentCore API used to invoke a runtime server-to-server. The caller needs the IAM action bedrock-agentcore:InvokeAgentRuntime on the target's ARN.
  • Execution role (per agent): each runtime assumes its own IAM role at runtime. That role's permissions are the upper bound of what that agent can do. One role per agent = blast-radius isolation.
  • Trust policy (AssumeRole): the policy on a role that says who may assume it. Ours only lets the AgentCore service assume the role, scoped to this account + region.
  • Workload Identity / Session: AgentCore gives each running agent a short-lived signed identity derived from its execution role; that is what signs the outbound A2A call.

2. Architecture — the delegation graph and who may call whom

3. The two controls that make an A2A hop safe

An A2A call is safe only if both are true: the caller is who it claims (authentication) and is allowed to call that target (authorization).

(a) Authentication — who is calling

The caller signs the request with SigV4 using its per-agent execution role. AWS verifies the signature; there is no bearer token on the wire to steal. The target runtime's trust policy ensures only the AgentCore service (not an arbitrary principal) can assume these roles:

// trust policy on every agent execution role (verified live)
{
  "Effect": "Allow",
  "Principal": { "Service": "bedrock-agentcore.amazonaws.com" },
  "Action": "sts:AssumeRole",
  "Condition": {
    "StringEquals": { "aws:SourceAccount": "001961766007" },
    "ArnLike":      { "aws:SourceArn": "arn:aws:bedrock-agentcore:us-east-1:001961766007:*" }
  }
}

(b) Authorization — who may call whom

The caller's role must hold bedrock-agentcore:InvokeAgentRuntime on the target. We grant this via one managed policy, scoped to our project's runtimes only:

// sre-agentic-dev-a2a-invoke  (verified live)
{
  "Sid": "InvokeSpecialistRuntimes",
  "Effect": "Allow",
  "Action": ["bedrock-agentcore:InvokeAgentRuntime"],
  "Resource": [
    "arn:aws:bedrock-agentcore:us-east-1:001961766007:runtime/sre_agentic_dev_*",
    "arn:aws:bedrock-agentcore:us-east-1:001961766007:runtime/sre_agentic_dev_*/runtime-endpoint/*"
  ]
}
Finding surfaced here: wildcard on the resource The policy allows invoking any sre_agentic_dev_* runtime, not only the specific targets each agent actually calls. It is scoped to our project (good — can't invoke unrelated runtimes) but it is not least-privilege within the project (the telemetry agent could invoke the supervisor, which it never needs to). Tracked as F3-A below. The callable graph is nonetheless constrained by the env wiring (next section) — agents only hold the ARNs they are meant to call.

6. Security assessment

Strengths

  • No bearer token on internal hops — SigV4 means there is no token to steal/replay between agents; identity is the request signature.
  • Per-agent roles — one execution role per runtime; a compromised agent cannot assume another's permissions (blast-radius isolation).
  • Deny-by-default — a runtime without the invoke policy simply cannot call another runtime (AWS IAM default deny).
  • Tight trust policy — only the AgentCore service can assume these roles, scoped to this account + region (no cross-account assume).
  • Correct split — JWT at the edge (Layer 1), SigV4 inside — the recommended AgentCore pattern.

Findings

F3-A · Medium A2A invoke policy is project-wildcarded, not per-target. It allows invoking any sre_agentic_dev_* runtime rather than only the specific targets each caller needs. Within-project least privilege is not achieved (e.g. telemetry-role could invoke the supervisor). Recommend splitting into per-caller policies listing only the exact target ARNs (matching the env wiring). The chicken-and-egg that motivated the wildcard (role needs the ARN, ARN needs the role) is solvable by referencing target ARNs by their deterministic name pattern per caller.
F3-B · Observation Callable graph is enforced by env wiring + IAM together. This works but splits the "who-can-call-whom" truth across two places (IAM policy + env vars). Consolidating the restriction into IAM (F3-A) makes the authorization model single-source and auditable.
F3-C · Good practice confirmed The tools runtime holds no invoke policy. Leaf services that call nobody are correctly denied any A2A invoke capability — verified (tools-role absent from the policy's attached entities).
Verdict Layer 3 is solid: internal hops are IAM-authenticated with per-agent roles and deny-by-default, and the trust policies are tight. The one real hardening item is F3-A — tighten the invoke policy from project-wildcard to per-target to achieve least privilege within the project. This will reappear in Layer 7 (IAM least-privilege audit) as a priority remediation.

7. Appendix — AWS SigV4 in depth (the cryptography behind every internal hop)

Every arrow in this layer is authenticated with AWS Signature Version 4 (SigV4). Because it is the backbone of all our service-to-service security (A2A hops and agent→tool calls), this appendix explains exactly what it is, which cryptographic primitives it uses, and walks the sign and verify steps for two real calls in this platform.

7.1 What SigV4 is — and is not

SigV4 is a request-signing protocol, not an encryption protocol. It proves three things about an HTTP request to AWS:

  • Authentication — the request was made by a principal holding specific AWS credentials (here, an agent's execution-role credentials).
  • Integrity — the signed parts of the request (method, path, key headers, and a hash of the body) were not altered in transit.
  • Freshness / anti-replay — the signature is bound to a timestamp and expires, and the credential scope binds it to one date, region, and service.
Key point SigV4 does not hide the payload — confidentiality is provided by TLS (HTTPS), which wraps the whole thing. SigV4 sits inside TLS and answers "who sent this and was it tampered?", while TLS answers "can anyone on the wire read it?". The two are complementary and both are always present on these calls.

7.2 The cryptographic primitives

PrimitiveAlgorithmRole in SigV4
HashingSHA-256Hashes the canonical request and the request body (payload hash).
Keyed MACHMAC-SHA256Used repeatedly to derive the signing key and to produce the final signature. HMAC = a hash that also takes a secret key, so only a holder of the key can produce or verify it.
Algorithm labelAWS4-HMAC-SHA256The string AWS puts in the Authorization header declaring the scheme.
Secret materialSecret access key (+ session token)The per-agent role's temporary credentials. The secret key is never sent — it only ever appears as an HMAC key on both sides.
Why HMAC and not a digital signature (RSA/ECDSA)? SigV4 is a symmetric scheme: the caller and AWS both hold the secret access key, so HMAC-SHA256 (fast, symmetric) is used rather than asymmetric signing. Contrast this with the Layer-1 JWT, which is asymmetric (RS256): Cognito signs with a private key and AgentCore verifies with the public key. Two different crypto models for two different trust relationships — symmetric HMAC between a principal and AWS (both hold the key), asymmetric RSA between an issuer and any verifier (only the issuer holds the private key).

7.3 How signing works (the 4 canonical steps)

When the supervisor container calls invoke_agent_runtime(...), the AWS SDK (botocore) performs these steps automatically using the supervisor role's temporary credentials:

STEP 1 — Canonical Request  (a deterministic, normalized form of the request)
  CanonicalRequest =
      HTTPMethod            e.g. POST
    + CanonicalURI          /runtimes/{urlEncodedInvestigatorArn}/invocations
    + CanonicalQueryString  qualifier=DEFAULT
    + CanonicalHeaders      host;x-amz-date;x-amz-security-token (sorted, lowercased)
    + SignedHeaders         the list of those header names
    + HashedPayload         SHA256(body)            <-- integrity over the body
  → hash it:  CR_HASH = SHA256(CanonicalRequest)

STEP 2 — String To Sign  (binds the request hash to a time + scope)
  StringToSign =
      "AWS4-HMAC-SHA256"
    + Timestamp             20261027T065152Z
    + CredentialScope       20261027/us-east-1/bedrock-agentcore/aws4_request
    + CR_HASH

STEP 3 — Derive the Signing Key  (chained HMACs — this is the clever part)
  kDate    = HMAC-SHA256("AWS4" + SecretAccessKey, "20261027")
  kRegion  = HMAC-SHA256(kDate,    "us-east-1")
  kService = HMAC-SHA256(kRegion,  "bedrock-agentcore")
  kSigning = HMAC-SHA256(kService, "aws4_request")
  // the signing key is scoped to date+region+service — it cannot sign for another
  // service or another day, which limits what a leaked derived key could do.

STEP 4 — Signature + Authorization header
  Signature = HEX( HMAC-SHA256(kSigning, StringToSign) )
  Authorization: AWS4-HMAC-SHA256
     Credential=<ACCESS_KEY_ID>/20261027/us-east-1/bedrock-agentcore/aws4_request,
     SignedHeaders=host;x-amz-date;x-amz-security-token,
     Signature=<64-hex-chars>
  (plus X-Amz-Security-Token: <session token> because these are temporary role creds)

7.4 How verification works (AWS side)

AWS receives the request and does the mirror image — it already knows the secret key for that access-key-id, so it re-derives everything and compares:

1. Parse Authorization header → get AccessKeyId, CredentialScope, SignedHeaders, Signature
2. Look up the SecretAccessKey for that AccessKeyId (and validate the session token)
3. Rebuild the CanonicalRequest from the actual received request
     → recompute SHA256(body); if the body was altered, this hash differs → FAIL
4. Rebuild StringToSign (checks the x-amz-date is within the allowed skew → anti-replay)
5. Re-derive kSigning (date/region/service from the credential scope)
6. ExpectedSignature = HMAC-SHA256(kSigning, StringToSign)
7. constant-time compare ExpectedSignature == provided Signature
     match   → identity confirmed = the role that owns that key
     mismatch→ SignatureDoesNotMatch / request rejected
8. ONLY THEN evaluate IAM authorization (does this role allow the action on this resource?)
Authentication vs authorization — two distinct gates Steps 1–7 are authentication (is the signature valid → who is this?). Step 8 is authorization (is that identity allowed? → the a2a-invoke policy from §3b). A request can pass authentication yet fail authorization (valid signature, but the role lacks InvokeAgentRuntime → that is our "Failure 1" in §4A, an AccessDeniedException).

7.6 Worked example B — agent → tool: telemetry → tools (via the Gateway)

The telemetry specialist fetches evidence by invoking the tools backend. In our architecture the agent presents a JWT to the Gateway (Layer 4), and then the Gateway uses SigV4 with its own gateway-role to invoke the downstream tools Lambda. So a single tool call actually uses both crypto models in sequence — a good illustration of where each belongs:

telemetry agent ──(1) JWT Bearer, RS256──▶  AgentCore Gateway  ──(2) SigV4, HMAC-SHA256──▶  tools Lambda

(1) Inbound to the gateway  = ASYMMETRIC (JWT / RS256)
    - the agent presents a Cognito M2M bearer token
    - gateway/AgentCore verifies it with Cognito's PUBLIC key (Layer 1 mechanism)
    - answers: "is this a known, allowed caller?"

(2) Outbound from the gateway = SYMMETRIC (SigV4 / HMAC-SHA256)
    - the gateway signs lambda:InvokeFunction with the GATEWAY-ROLE temporary creds
    - service = "lambda", region = us-east-1  (note: different service → different kService)
    - AWS verifies the signature with the gateway-role key, then checks the gateway-role
      is allowed lambda:InvokeFunction on sre-agentic-dev-tools  (Layer 4 least-privilege)
    - answers: "is the gateway itself allowed to run this specific tool?"
Why this matters for the security story The same tool call is protected by asymmetric crypto on the caller-facing side (JWT, to verify identity without sharing a secret) and symmetric crypto on the AWS-facing side (SigV4, between the gateway and AWS which both hold the key). Each model is used exactly where its trust assumptions fit. We detail the Gateway's role and least-privilege in Layer 4; this appendix just shows the cryptography underneath it.

7.7 Threats SigV4 defends against (and what it does not)

ThreatDefended?How / caveat
Impersonating another agentYesCannot produce a valid signature without that role's secret key.
Tampering with the request bodyYesSHA-256 payload hash is inside the signature; any change breaks it.
Replaying a captured request laterYesTimestamp + clock-skew window; temporary creds also expire.
Reading the payload on the wireN/AThat is TLS's job, not SigV4's — TLS is always present on these HTTPS calls.
A leaked long-lived secret keyPartialSigV4 can't help if the key is stolen — but these are short-lived role session creds, so the exposure window is minutes-to-hours, not forever.
An over-broad IAM policyNoSigV4 only authenticates; authorization is IAM's job — see finding F3-A (wildcard invoke policy).

7.8 Where does the shared secret come from? (symmetric key, never transmitted)

A natural question: SigV4 is symmetric, so both the caller and AWS must hold the same secret key — how does that happen without the key ever being sent on the request? The answer is that AWS itself mints the key and hands a copy to the caller when the agent assumes its role. There are only ever two holders: the calling agent and AWS (STS/IAM).

  1. AssumeRole: the AgentCore runtime assumes its execution role (e.g. supervisor-role) via sts:AssumeRole.
  2. STS mints & delivers: AWS STS generates a fresh temporary credential set — AccessKeyId (identifier, starts with ASIA), SecretAccessKey (the HMAC secret), and a SessionToken — and gives them to the agent. STS/IAM also keeps its own record of which secret belongs to that AccessKeyId.
  3. Request carries the id, not the secret: the agent signs with the SecretKey and sends only the AccessKeyId + the computed Signature (and the SessionToken). The secret never leaves the agent.
  4. Verify by lookup: AWS reads the AccessKeyId from the header, looks up the matching SecretKey in its own store, recomputes the HMAC, and compares. Match → identity proven.
Why symmetric is safe here — and why the JWT is asymmetric instead SigV4 can be symmetric because AWS is both the key-issuer and the only verifier — it safely shares a copy of the key with the one caller it issued it to, and no third party ever needs to verify. The Layer-1 JWT is the opposite situation: the verifier (AgentCore) must check tokens without being able to mint them, so it uses asymmetric RS256 — only Cognito holds the private key (can sign), while anyone can verify with the public key (JWKS). Same goal (prove identity), different trust shape, different crypto.

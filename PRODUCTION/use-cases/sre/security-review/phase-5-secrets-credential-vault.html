Layer 5 — Secrets & Credential Vault

Where every secret lives, how it reaches the point of use, and why the agent code and the LLM never possess one.

1. What this layer is

Every system has secrets — here, the Cognito M2M client secret an agent uses to get a gateway token, and the ticketing API key used to create a ticket. The security question is not "do we have secrets" (we always will) but: where do they live at rest, how do they travel to the point of use, and who can see them along the way? The worst outcome in an agentic system is a secret reaching the LLM — because a prompt-injected model could then leak it. Layer 5 shows that in this platform a secret is never in agent code, never in an environment variable, never in a tool argument, never in the LLM context, and never in logs.

Terminology
  • AWS Secrets Manager: the managed store that holds secret bytes at rest, encrypted, with IAM-controlled read access and audit via CloudTrail. The physical home of a secret.
  • AgentCore token vault / credential provider: a logical credential registered in AgentCore Identity (e.g. an API_KEY provider). It is referenced by ARN; its actual bytes are kept in an AgentCore-managed Secrets Manager secret. The vault is what the Gateway talks to via GetResourceApiKey.
  • Secret ARN vs. secret value: an ARN is a non-sensitive pointer (arn:aws:secretsmanager:...:secret:name); the value is the bytes. We only ever put ARNs in env vars/config; values are fetched at runtime with an IAM-scoped read.
  • Just-in-time fetch: the pattern of reading a secret only at the moment of use and holding it in memory briefly, rather than injecting it into the environment at startup.
  • AWS-managed secret (service-name!...): a Secrets Manager secret whose name is prefixed with an owning service (here bedrock-agentcore-identity!). It is owned and lifecycle-managed by that AWS service, not created directly by us.

3. The two credential journeys

3.1 The agent's gateway secret (self-service fetch)

A specialist needs a Cognito token to call the gateway. It does not have the client secret baked in — it has the ARN of the secret and fetches the value at runtime:

// on the runtime (verified live): env var is a POINTER, not the secret
SRE_GATEWAY_CLIENT_SECRET_ARN = arn:aws:secretsmanager:us-east-1:001961766007:secret:sre-agentic-dev-gateway-caller-Ty3zOA

// at call time, inside the container:
1. secretsmanager:GetSecretValue(SRE_GATEWAY_CLIENT_SECRET_ARN)   // IAM-scoped to THIS one secret
   → { "client_id": "...", "client_secret": "..." }
2. POST Cognito /oauth2/token  (Basic client_id:client_secret, grant=client_credentials)
   → JWT
3. call the gateway with Bearer JWT
// the client_secret lives in memory only during step 1-2; never in env, never logged

The IAM permission for step 1 is scoped to exactly that one secret (verified):

// sre-agentic-dev-gateway-secret  (attached to the 4 tool-using agent roles)
{
  "Sid": "ReadGatewayCallerSecret",
  "Effect": "Allow",
  "Action": ["secretsmanager:GetSecretValue"],
  "Resource": "arn:aws:secretsmanager:us-east-1:001961766007:secret:sre-agentic-dev-gateway-caller-Ty3zOA"
}

3.2 The ticketing API key (gateway-injected, agent never touches it)

This is the stronger pattern — the agent never fetches or sees the key at all; the gateway does the fetch-and-inject. (Full step-by-step and diagram are in Layer 4 §5.2.) Summary:

remediation agent → Gateway (tools/call create_ticket, NO key in request)
  Gateway (using gateway-role):
     GetWorkloadAccessToken + GetResourceApiKey  → token vault provider sre-ticketing-apikey
        → AgentCore Identity reads the AWS-managed secret (secretsmanager:GetSecretValue)
     → raw key held in gateway memory, briefly
     → outbound POST /tickets  with  x-api-key: <key>   (injected by the gateway)
  → ticket created; key never returned to the agent, never in the MCP response

4. The central guarantee — a secret never reaches the LLM

Trace every place a secret could end up and confirm it does not:

PlaceContains a secret?Evidence
Agent source codeNoCode references ARNs/env var names, never literal secret values.
Runtime environment variablesNoLive scan (below): only ARNs, ids, URLs. e.g. SRE_GATEWAY_CLIENT_SECRET_ARN is an ARN.
Tool-call argumentsNoThe ticketing call carries title/tenant_id/severity — never api_key.
LLM prompt / contextNoSecrets are fetched by non-LLM code (container / gateway); the model is never given one.
MCP tool responseNoThe gateway returns the ticket result, not the injected key.
Logs / tracesCaveatSecrets are not logged. BUT Layer 6/8 note: LLM prompts + tool I/O are on spans (eval requirement). Since no secret is ever in prompts/args, this is safe — but it is why "no secret in args/prompt" must hold absolutely. Cross-ref finding in Layer 8.
Why this matters uniquely for agentic systems In a traditional service, "don't log the secret" is enough. In an agentic system there is an extra adversary: the LLM itself, which can be prompt-injected into trying to exfiltrate whatever it can see. The defense is structural: the model is simply never given a secret. The container (for the gateway token) and the gateway (for the API key) handle credentials in code paths the LLM has no access to. You cannot leak what you were never given.

6. Security assessment

Strengths

  • Only two secrets, both in managed stores — nothing home-rolled; both sit in AWS Secrets Manager, encrypted at rest, IAM-gated, CloudTrail-audited.
  • Pointers, not values, in config — runtimes carry secret ARNs; the bytes are fetched just-in-time. Verified by a live env scan showing zero raw secret values.
  • LLM never possesses a secret — credentials are handled by container/gateway code paths the model cannot reach; nothing credential-bearing is in prompts, tool args, or MCP responses.
  • Scoped reads — the agent secret-read policy is restricted to exactly one secret ARN (no wildcard); the gateway's vault access is restricted to the one ticketing provider.
  • Gateway-injected API key — for the external call, the agent never even fetches the key; the gateway fetches and injects it, so the key's exposure is limited to the gateway's memory for the duration of one call.

Findings

F5-A · Medium · to improve No secret rotation. Both secrets have RotationEnabled = null (verified). The Cognito M2M client_secret and the ticketing API key are long-lived. Remediation: enable Secrets Manager automatic rotation (or, for the Cognito M2M case, migrate to private-key-JWT client auth so there is no shared secret to rotate at all). Pairs with finding F1-A. Target: P5.
F5-B · Low/Med · to improve No customer-managed KMS key. The gateway-caller secret shows KmsKeyId = null — it is encrypted with the AWS-managed Secrets Manager key, not a customer-managed key (CMK). A CMK gives you key-level access policy, rotation control, and an independent audit/deny point. Remediation: encrypt the secret(s) with a dedicated CMK scoped to the agent/gateway roles. Target: P5.
F5-C · Observation (depends on F4-D/F4-E) Any specialist can obtain the gateway token. The one gateway-caller secret is readable by all four tool-using agent roles (by design today). Combined with the lack of per-agent scope (F4-D), this means any specialist can mint a gateway token and reach any tool. Tightening per-agent identity (F4-D) and splitting secrets per agent would reduce this shared-credential blast radius.
F5-D · Good practice confirmed No secret material in environment or code. Live env scan across runtimes shows only ARNs, ids, and URLs — the "secret" env var is explicitly an ARN pointer. Verified.
Verdict Layer 5 is architecturally strong: two secrets, both in managed stores, referenced by ARN, fetched just-in-time, scoped by IAM, and — the property that matters most in an agentic system — never reachable by the LLM. The hardening debt is lifecycle, not architecture: enable rotation (F5-A), add a CMK (F5-B), and reduce the shared-credential blast radius once per-agent identity (F4-D) lands. None of these are leaks; they are defense-in-depth upgrades for P5.

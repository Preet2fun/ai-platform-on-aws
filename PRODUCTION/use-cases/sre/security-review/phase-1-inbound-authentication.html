Layer 1 — Inbound Authentication

Who is allowed to call the platform at all, and how that is proven before any agent code runs.

1. What this layer is

The supervisor runtime is the single front door to the entire platform. Every incident investigation enters here. Inbound authentication is the control that decides whether a caller is even allowed to reach the supervisor's application code. If this layer is weak, nothing behind it matters.

We enforce inbound auth with an AgentCore inbound JWT authorizer backed by Amazon Cognito using the OAuth 2.0 client-credentials grant (machine-to-machine). The AgentCore platform validates the caller's token — signature, expiry, issuer, and client id — before the request is handed to our container. Our code never sees an unauthenticated request.

Terminology — the pieces, in AWS terms
  • JWT (JSON Web Token): a signed, base64url token with three parts (header.payload.signature). The payload carries "claims" (who, what scope, when it expires). Signed by the issuer so it can't be forged or tampered with.
  • Amazon Cognito User Pool: AWS's managed identity provider (IdP). It issues and signs the JWTs. Ours is M2M-only — it mints tokens for services, not human logins.
  • App Client: a registered caller identity inside the pool. Each has a client_id and a client_secret. We create one app client per tenant (acme-retail, globex-fintech) plus one for internal gateway calls.
  • Client-credentials grant (2-legged OAuth / "M2M"): the OAuth flow where a service authenticates as itself (not on behalf of a human) using its client_id + client_secret to get an access token.
  • Resource Server: a Cognito construct that defines the custom scopes a token can carry for "your API." It is not a server you run — it is a namespace of permissions. Ours is named sre-api and defines one scope, sre-api/invoke. A client-credentials token is only issued if the client is allowed that scope. Think of it as "the catalogue of permissions the pool is allowed to stamp into a machine token."
  • Discovery URL (OIDC): a well-known metadata URL Cognito publishes (/.well-known/openid-configuration). AgentCore reads it to find Cognito's public signing keys (JWKS) so it can verify token signatures automatically.
  • Inbound JWT Authorizer (AgentCore): runtime configuration that tells AgentCore "only accept requests carrying a valid JWT from this issuer, for these client ids." Validation happens at the platform edge.

3. Request / response flow (production example: tenant acme-retail)

Here is the exact two-step flow a real caller performs. Step A gets a token from Cognito; step B calls the supervisor with it. Both are shown with real values from this account.

Step A — obtain an M2M access token

POST https://sre-agentic-dev-auth.auth.us-east-1.amazoncognito.com/oauth2/token
Authorization: Basic base64(client_id:client_secret)     # acme-retail client
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&scope=sre-api/invoke

→ 200 OK
{ "access_token": "eyJraWQ...", "expires_in": 3600, "token_type": "Bearer" }

Step B — invoke the supervisor with the Bearer token

POST https://bedrock-agentcore.us-east-1.amazonaws.com/runtimes/
     {urlEncodedSupervisorArn}/invocations?qualifier=DEFAULT
Authorization: Bearer eyJraWQ...
Content-Type: application/json
X-Amzn-Bedrock-AgentCore-Runtime-Session-Id: <uuid>

{ "scenario_id": "rds-connection-exhaustion",
  "alarm": "checkout-api-5xx-high — connection pool exhausted" }
          ^ note: NO tenant_id in the body — tenant is derived from the token (Layer 2)

→ 200 OK  (full investigation result)
Why the AgentCore platform, not our code, validates the token Validation happens at the platform edge. By the time /invocations reaches our container, AgentCore has already checked the signature (against Cognito's JWKS), expiry, issuer, and that client_id is in the allow-list. A bug in our app can therefore never accidentally accept an unauthenticated request — the request would never arrive.

Critical observation for the whole review The token proves which client (client_id) and what scope — but it carries no tenant claim. So this layer proves "a known, allowed machine is calling." It does not by itself decide which tenant's data the caller may touch. That tenant decision is made one layer deeper, in the supervisor, by mapping this verified client_id → a tenant (see Layer 2 — Tenant Identity & Isolation). This split is deliberate and is the hinge of our multi-tenant isolation story.

7. Security assessment

Strengths

  • Platform-enforced — auth is checked before our code runs; an app bug cannot expose an unauthenticated path.
  • OAuth-only front door — SigV4 is proven to be rejected; there is no dual auth path to exploit.
  • Short-lived tokens (1h) and per-tenant clients give per-caller revocability and blast-radius containment.
  • No human-login surface (M2M-only pool) shrinks the attack surface.

Findings

F1-A · Medium Long-lived client secrets. M2M client secrets do not auto-rotate. Recommend a rotation schedule, or migrate to private-key-JWT client auth (no shared secret at all).
F1-B · By design Scope does not encode tenant. Any allowed client with sre-api/invoke passes this layer; tenant enforcement is deliberately deferred to Layer 2 (client_id→tenant mapping). For a large tenant fleet, consider per-tenant scopes (e.g. sre-api/tenant.acme-retail) so the token itself is tenant-bound.
F1-C · Low Static allow-list. Adding a tenant requires redeploying the supervisor's authorizer config (allowedClients). Operational friction, not a vulnerability.
F1-D · Low/Med No WAF / per-caller rate limiting at the inbound edge beyond AgentCore's built-in throttling. Consider if the endpoint becomes externally reachable by untrusted networks.
Verdict Layer 1 is solid and enforced. The front door accepts only known, signed, unexpired M2M tokens and rejects everything else at the platform edge. Findings are hardening items, not holes. The one thing to carry forward: the token authenticates a client, not a tenant — Layer 2 is where that becomes an enforced isolation boundary.

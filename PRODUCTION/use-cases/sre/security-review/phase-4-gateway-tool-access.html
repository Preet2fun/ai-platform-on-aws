Layer 4 — Tool Access Control (Gateway)

How agents reach tools through a single, policy-enforced choke point — JWT inbound, least-privilege IAM outbound.
Account: 001961766007 Region: us-east-1 Gateway: sreagenticdevgw (MCP) Inbound: CUSTOM_JWT · Outbound: GATEWAY_IAM_ROLE Status: Enforced · Verified live

1. What this layer is

Agents need tools — the specialists read metrics, logs, traces, changes, events and runbooks to gather evidence. The security question is: how does an agent reach a tool, and what stops an agent (or a compromised agent) from reaching a tool or data it shouldn't?

Rather than let every agent hold direct credentials to every backend, all tool access flows through one AgentCore Gateway — a managed MCP server that is the single choke point for tools. The gateway does two security jobs: it authenticates the caller inbound (Cognito JWT), and it invokes the backend outbound using its own least-privilege IAM role — so no agent ever holds direct invoke rights on the tool backends. This is the architectural win of Layer 4: tool authorization is centralized and auditable in one place.

Terminology
  • MCP (Model Context Protocol): an open protocol for exposing "tools" to agents in a uniform way (list tools, call a tool). The gateway speaks MCP to the agents.
  • AgentCore Gateway: a managed service that turns backends (Lambda, OpenAPI/REST, Smithy, other MCP servers) into MCP tools behind one endpoint, handling inbound auth, outbound auth, and protocol translation.
  • Target: one backend wired into the gateway. We have two: sretools (the 6 observability tools, backed by a Lambda) and ticketing (a demo external API, Layer 5).
  • Inbound authorization: who may call the gateway. Ours = CUSTOM_JWT (the same Cognito pool as Layer 1).
  • Outbound authorization: how the gateway authenticates to the backend. For the tools Lambda we use GATEWAY_IAM_ROLE — the gateway signs the invoke with its own IAM role (SigV4, exactly the §7.6 pattern from Layer 3's appendix).
  • Tool name prefixing: the gateway exposes tools as <target>___<tool> (e.g. sretools___metrics) so names can't collide across targets.

2. Architecture — one choke point, two auth edges

3. The two security edges

(a) Inbound — only known clients can call the gateway

The gateway is CUSTOM_JWT, validating tokens from the same Cognito pool as Layer 1. Its allow-list includes the two tenant clients and the internal gateway-caller client (used by the specialists to reach the gateway):

// gateway authorizer (verified live)
authorizerType: CUSTOM_JWT
customJWTAuthorizer:
  discoveryUrl: https://cognito-idp.us-east-1.amazonaws.com/us-east-1_wWlzIHoRM/.well-known/openid-configuration
  allowedClients:
    - 66f0eb5m3ri4ad02d6hjjd37db   # acme-retail
    - 5cnjgnqi4o2avg62egtu6be4tt   # globex-fintech
    - 62qumqhsk7tnhsg817j2gjhc48   # gateway-caller (internal, Layer 3/5)

(b) Outbound — the gateway's own least-privilege role

This is the heart of Layer 4. The gateway invokes the tools backend with its own IAM role, and that role is scoped to exactly one action on exactly one function — nothing else:

// sre-agentic-dev-gateway-role → inline policy "invoke-tools-lambda" (verified live)
{
  "Sid": "InvokeToolsLambda",
  "Effect": "Allow",
  "Action": "lambda:InvokeFunction",
  "Resource": "arn:aws:lambda:us-east-1:001961766007:function:sre-agentic-dev-tools"
}
The deliberate contrast — no AdministratorAccess A commonly-flagged AgentCore anti-pattern is a Gateway service role with broad or AdministratorAccess permissions (the gateway role is shared across all targets, so its permissions are the upper bound of what any caller can reach through it). Ours has zero managed policies and two tightly-scoped inline policies: invoke-tools-lambda (one function ARN) and ticketing-apikey-outbound (Layer 5). The upper bound of "what any agent can do through the gateway" is therefore: invoke that one Lambda, and fetch that one API key.

4. Request / response flow (telemetry agent calls the metrics tool)

1. telemetry agent → Gateway  (MCP "tools/call" over HTTPS)
     Authorization: Bearer <Cognito M2M JWT>            # inbound auth
     { name: "sretools___metrics",
       arguments: { tenant_id: "acme-retail",            # tenant carried in args (Layer 2/6)
                    scenario_id: "rds-connection-exhaustion", service: "product-db" } }

2. Gateway verifies the JWT (allowedClients) → client known
3. Gateway routes by tool name → target "sretools" → tools Lambda
4. Gateway invokes the Lambda, SIGNED WITH gateway-role (SigV4 lambda:InvokeFunction)
     - the AGENT never had lambda:InvokeFunction; only the gateway does
5. tools Lambda enforces tenant scoping on the args (Layer 6) and returns metrics JSON
6. Gateway returns the MCP tool result to the agent

4A. End-to-end sequence — tool call vs. failure modes

5. Detailed request/response flow — the two tool-call types

The gateway fronts two kinds of target, and they use different outbound auth. Walking both end-to-end shows exactly how a request travels and — for the ticketing case — how a secret moves from Secrets Manager into the outbound API call without ever touching the agent or the LLM.

5.1 Type A — Lambda target (sretools): read observability evidence

Outbound auth = GATEWAY_IAM_ROLE (SigV4). This is the path used for all six metrics/logs/traces/changes/events/runbooks tools.

REQUEST  (telemetry agent → Gateway, MCP over HTTPS)
  POST https://sreagenticdevgw-xgroozgkst.gateway.bedrock-agentcore.us-east-1.amazonaws.com/mcp
  Authorization: Bearer <Cognito M2M JWT (gateway-caller)>
  { "method": "tools/call",
    "params": { "name": "sretools___metrics",
                "arguments": { "tenant_id": "acme-retail",
                               "scenario_id": "rds-connection-exhaustion",
                               "service": "product-db" } } }

GATEWAY INTERNAL
  1. verify JWT against Cognito JWKS; client_id ∈ allowedClients?         → yes
  2. parse tool name "sretools___metrics" → target=sretools, tool=metrics
  3. outbound auth for this target = GATEWAY_IAM_ROLE
  4. build Lambda Invoke request; SIGN with gateway-role temp creds (SigV4, service=lambda)
       Action evaluated: lambda:InvokeFunction on arn:...:function:sre-agentic-dev-tools  → ALLOW
  5. invoke the Lambda with payload { tool:"metrics", arguments:{...} }

LAMBDA (sre-agentic-dev-tools)
  6. reads BUNDLED synthetic-data files for tenant_id=acme-retail only   (tenant scope, Layer 6)
     - rejects a scenario that doesn't belong to the tenant → 404
  7. returns metrics JSON

RESPONSE
  8. Gateway wraps the Lambda result as an MCP tool result → back to the agent
     (the agent/LLM only ever see tool INPUT args + OUTPUT data — never any AWS credential)
Who signs, who holds what The agent held only a JWT (identity to the gateway). The gateway held the IAM role that can invoke the Lambda. The Lambda held no outbound credentials at all (reads bundled files). Three parties, each with the minimum it needs, and no AWS secret ever reaches the agent.

5.2 Type B — OpenAPI target (ticketing): the API key travels Secrets Manager → Gateway → external API

Outbound auth = API_KEY from the AgentCore token vault. This is the credential- injection flow — the security-critical part of your question: how does the stored key get onto the outbound HTTPS call without the agent or LLM ever seeing it?

REQUEST  (remediation agent → Gateway, MCP over HTTPS)
  Authorization: Bearer <Cognito M2M JWT>
  { "method": "tools/call",
    "params": { "name": "ticketing___create_ticket",
                "arguments": { "title": "RDS pool exhaustion — product-db",
                               "tenant_id": "acme-retail", "severity": "high" } } }
  // NOTE: no api_key anywhere in the request. The agent does not have it and cannot send it.

GATEWAY INTERNAL — credential injection
  1. verify JWT (allowedClients)                                          → ok
  2. tool "ticketing___create_ticket" → target=ticketing, outbound=API_KEY
  3. the gateway must fetch the key. Using its gateway-role, it calls AgentCore Identity:
       a. GetWorkloadAccessToken   (proves the gateway's own workload identity)
       b. GetResourceApiKey        (on credential provider token-vault/.../sre-ticketing-apikey)
  4. AgentCore Identity resolves the provider → reads the backing secret:
       secretsmanager:GetSecretValue
         arn:...:secret:bedrock-agentcore-identity!default/apikey/sre-ticketing-apikey-*
       (this secret is AWS-managed, owned by the AgentCore Identity service)
  5. the gateway now holds the raw API key IN MEMORY, briefly
  6. it reads the ticketing OpenAPI schema from S3 to know the operation + where the key goes
       s3:GetObject  s3://sre-agentic-dev-artifacts-.../schemas/...
  7. OUTBOUND call to the external ticketing API, key INJECTED into the configured location
       POST https://<ticketing-api>/tickets
       x-api-key: <raw key from the vault>          ← injected by the gateway, not the agent
       { "title": "...", "tenant_id": "acme-retail", "severity": "high" }

RESPONSE
  8. ticketing API → 201 { "ticket_id": "INC-12345" }
  9. Gateway returns the ticket result to the agent as an MCP tool result
     (the raw api_key never appears in the MCP response, the agent, the LLM, logs, or tool args)
The security property this delivers The API key lives at rest in AWS Secrets Manager (an AWS-managed secret owned by AgentCore Identity), is referenced logically through the token vault credential provider, and is fetched and injected by the gateway just-in-time on the outbound call. The agent code and the LLM never possess the key — it is not in the tool arguments, not in the MCP response, not in env vars, not in logs. Even a fully prompt-injected model cannot exfiltrate a secret it is never given. (Layer 5 examines this credential model in full.)

7. Security assessment

Strengths

  • Single choke point — all tool access is centralized at one gateway; authorization is in one auditable place, not scattered across agents.
  • Agents hold no backend credentials — only the gateway can invoke the tool Lambda; a compromised agent cannot reach the backend directly (deny-by-default).
  • Gateway role is genuinely least-privilege — no managed policies, one action on one function ARN. The deliberate opposite of the AdministratorAccess anti-pattern.
  • Backend role is minimal too — the tools Lambda can only write logs; no lateral movement possible from it.
  • Inbound JWT reuses the same trust root as Layer 1 (one Cognito pool, consistent auth).
  • Clean crypto split — JWT inbound (asymmetric), SigV4 outbound (symmetric) — exactly the §7.6 pattern.

Findings

F4-A · Low/Med Gateway allow-list mixes tenant and internal clients. The gateway accepts the two tenant clients and the gateway-caller. In our flow specialists use the gateway-caller identity, so the tenant clients may not strictly need gateway access. Recommend confirming whether tenant clients should be removed from the gateway's allowedClients (tighten to only the internal caller) to reduce the inbound surface.
F4-B · Observation Tenant isolation is not enforced by the gateway itself. The gateway authenticates the caller and invokes the Lambda, but the tenant scoping of the returned data is enforced inside the Lambda from the tenant_id argument (Layer 6). The gateway does not inspect tenant. This is acceptable (defense is one layer in) but means the gateway is not a tenant-isolation boundary — documented so the responsibility is explicit.
F4-C · Good practice confirmed No AdministratorAccess anywhere in the tool path. Both the gateway role and the Lambda role are minimal and scoped — verified live.
F4-D · Medium · to improve No per-agent identity or scope differentiation at the gateway. All specialist→gateway calls use a single shared gateway-caller Cognito client with one scope (sre-api/invoke), so every agent looks identical to the gateway and the inbound authorizer only checks allowedClients, not allowedScopes. A compromised specialist could call any tool the gateway exposes. Remediation: give each agent its own Cognito client, define per-capability scopes on the sre-api resource server (e.g. tools.read, ticketing.write), grant each agent only its scopes, and enforce allowedScopes at the gateway. Target: a later hardening phase (P5).
F4-E · Medium · to improve One shared signer for all tools of a target; no per-tool authorization. All six sretools tools are invoked by the single gateway-role on one Lambda, with no gate distinguishing read-only tools from any future sensitive/write tool. There is no policy engine deciding "this caller may call metrics but not create_ticket." Remediation: either (a) split sensitive/write tools into a separate target/backend with its own outbound credential, and/or (b) attach the AgentCore policy engine (Cedar) to the gateway for per-tool, per-caller authorization. Pairs with F4-D. Target: P5.
Verdict Layer 4 is strong on the outbound side: tool access is funneled through one gateway with a genuinely least-privilege outbound role, agents hold no backend credentials, and the backend role is minimal — avoiding the classic over-privileged-gateway gap. The inbound side has real hardening debt: there is no per-agent identity or per-tool authorization (F4-D, F4-E) — today any specialist can call any tool the gateway exposes. These are the priority improvements to carry into P5. Tenant data isolation lives one layer deeper — Layer 6.

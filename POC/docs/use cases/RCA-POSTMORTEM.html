Findings

1.1Tenant credentials unavailable — platform credentials substituted silently
AccessDenied: User: arn:aws:sts::001961766007:assumed-role/poc-backend-task-role/…
  is not authorized to perform: sts:AssumeRole
  on resource: arn:aws:iam::021448121605:role/MSP-poc_account-Role
The failure happens inline in the accept path (27.15 ms) and is downgraded to a warning. The request proceeds with the platform's own credentials, so later live-infrastructure checks query account 001961766007 rather than the tenant. The resulting report states “ECS tasks 2/2 running” and “Last deployment 3+ days ago” — which describe poc-backend-service in the platform account and the AgentCore runtimes last updated 2026-09-18. Nothing in the UI signals the substitution.
1.2Telemetry scoping held — 32 of 32 queries tenant-filtered
Every agent-authored SQL statement captured in the RDS statement log carried tenant_id = 'poc_account' — 32 of 32, zero unscoped. Enforcement is still only a prompt instruction with no database-level guarantee (no row-level security, no per-tenant DB role), so the control remains architecturally weak; but selecting the tenant did produce correct scoping on the telemetry path.
1.3Long-term memory is the largest accept cost and returned nothing
RetrieveMemoryRecords took 301.76 ms — 54% of the 560 ms accept path — and returned zero facts, confirmed by the absence of the LTM retrieval: N facts log line. The lookup runs unconditionally on every request. Combined with the failed credential resolution, about 78% of the accept path produced no usable result.
1.4The single-agent fast path is unavailable, forcing the full fan-out
The handler first attempts a direct investigator invocation for RCA-shaped questions. It raises NameError: boto3 is not defined — routes.py:623 calls boto3.client(…) while boto3 is only ever imported locally inside other functions — and a broad except Exception reduces it to a warning. Every RCA request therefore takes the three-runtime Supervisor path. Measured investigator-only share of this run is 65.35 s and roughly $0.24, against 146.36 s and $0.4332 actually spent.
1.5Identity is weaker than the multi-tenant model requires
The API is authorised with a Cognito ID token (token_use = id), which carries no scope, so there is no authorisation surface beyond “authenticated”. The token contains no tenant claim — tenant identity travels as a request body field that the server does not validate against the user. The AgentCore runtimes have authorizerConfiguration: null, so the only auth boundary is at the load balancer. Separately, because the SSE token is a query parameter, the full signed JWT is written to the backend access log in cleartext on every request.

Findings

2.1Memory has no tenant dimension
session_id = f"msp-{user_id}-{request.conversation_id}"
namespace  = f"/strategy/{_LTM_STRATEGY_ID}/actor/{user_id}/"
Both short-term and long-term memory are keyed on user and conversation only. If an operator investigates one tenant and then switches the dropdown to another within the same conversation, the first tenant's findings remain in session memory and are supplied to the model, and long-term facts derived from the first tenant's telemetry stay retrievable while working on the second. This is a separate isolation surface from the database path — scoping SQL by tenant_id does nothing to scope memory.
2.2The running model contradicts the deployment script
deploy.sh:1639 passes --env MODEL_ID=${MODEL:-…claude-haiku-4-5…}, yet the runtime logs model=global.anthropic.claude-sonnet-4-5-20250929-v1:0 — the hard-coded default at supervisor_runtime.py:33. The environment variable never took effect, matching get-agent-runtime reporting no MODEL_ID at all. Sonnet is 3× Haiku in both directions: the Supervisor's 3 calls in this run (13,604 in / 3,458 out) cost $0.0927 against $0.0309 on Haiku — roughly 21% of total run spend, for orchestration only.
2.3Orchestration overhead is re-paid every turn
1,971 input tokens and 7.35 s to select a single tool. The system prompt is ~790 tokens; the balance is the full 7-tool schema set plus the user message, retransmitted on each Supervisor turn regardless of which tools are plausible for the request.
2.4The agent graph is rebuilt on every new container
_graph is a module-global, so each instance pays 134 ms to construct the LangGraph agent. A second container cold-started mid-request at 11:33:57, so with AgentCore scale-out this cost recurs rather than amortising.
2.5Tenant authorisation is never checked
poc_account arrives as a request body field, is logged, and is passed straight to the specialist. At no point does the Supervisor verify that this operator is entitled to that tenant — there is no claim to compare against and no server-side entitlement lookup.

Findings

3.1Cost is dominated by re-reading prior results, not by querying
282,568 input tokens were consumed to issue 11 queries. LangGraph resends the entire message history each turn, so every SQL result is paid for repeatedly — by turn 16 the model re-reads roughly 35k tokens of accumulated output in order to decide one further query. This single step is 72% of the run's spend, and almost all of it is retransmitted context rather than new information.
3.2Tenant scoping verified in full
Eleven of eleven agent-authored queries filtered on tenant_id = 'poc_account', as recorded independently by PostgreSQL rather than inferred from the prompt. Enforcement remains prompt-based with no database-level guarantee — no row-level security and no per-tenant database role — but compliance in this run was total. This is the evidence behind Finding 1.2.
3.3The telemetry database is not a bottleneck
0.53 s of 65.35 s. Latency work belongs on the inference side — reducing turn count and context size — not on query tuning or indexing. Optimising SQL here would recover under one percent.
3.4Schema reflection repeats on every container
Fourteen pg_catalog statements plus three sample-row reads execute before any reasoning begins. _graph_cache is keyed per process, so each new instance pays the reflection cost again instead of reusing a cached schema.
3.5Final synthesis is one long call near its output ceiling
Call 16 ran 26.54 s — 41% of the investigator's wall time — and emitted 2,902 output tokens against a max_tokens of 4,096, i.e. 71% of the available budget. A longer or more detailed report has little headroom before it is truncated mid-generation.

Findings

4.1The specialist announces tenant scoping, then silently discards it
Using tenant-scoped boto3 tools for poc_account is logged before credentials are ever tested. The contradicting line is a WARNING, not an error, is never surfaced to the user, and repeats 22 times without escalating. An operator reading the logs at INFO level would conclude tenant isolation was working.
4.2Platform telemetry is presented as tenant fact
Four statements in the delivered RCA describe account 001961766007 while being attributed to the tenant. There is no marker in the output, and no confidence reduction, to indicate the live-validation section was answered from the wrong account.
4.3Absence of data was misread as a monitoring gap
The report concludes “Limited observability: no checkout/payment/DNS metrics in CloudWatch.” Those metrics are missing only because the wrong account was queried — the same run read them in volume from the tenant's telemetry database in Step 3. This is the most damaging failure mode of the four: it yields a confident, plausible and actionable recommendation that would send an engineer to instrument a service which is already fully instrumented.
4.4Credentials are re-resolved on every tool call
11 Secrets Manager reads in 11 seconds with no caching — roughly 600 ms of avoidable latency and 11 chargeable API calls per specialist invocation, all returning the same unusable secret.
4.5The AgentCore Gateway was bypassed
The specialist's spans show direct AWS SDK calls (aws.remote.service = AWS::CloudWatch / AWS::ECS / AWS::EC2) and the gateway vended log has no events for this window, whereas an earlier run in this environment produced 31 AgentCore.Gateway.InvokeTool spans. Gateway-level authorisation, tool allow-listing and audit therefore did not apply to these calls. Why the path differs between runs has not been established.
4.6Final synthesis is the single most expensive call in the run
43.49 s and $0.0642 — 15% of total spend in one call — emitting 2,987 output tokens against the 4,096 ceiling, i.e. 73% of budget consumed.

0. The worked scenario

We run a SaaS platform with two agents — a travel-agent and a shopping-agent — serving three customers:

tenant-acme

Users: u-1001, u-1002.
Uses both agents.

tenant-globex

Users: u-2001.
Uses travel-agent only.

tenant-initech

Users: u-3001, u-3002.
Uses shopping-agent only.

All of them share one memory resource (my_memory) and one IAM policy. Each user's long-term memory lives under its own composite namespace:

# actorId = {tenantId}:{agentId}:{userId}   →   namespace = /{actorId}/my_memory/
/tenant-acme:travel-agent:u-1001/my_memory/      # Acme user 1, travel
/tenant-acme:shopping-agent:u-1001/my_memory/    # same user, shopping — isolated
/tenant-acme:travel-agent:u-1002/my_memory/      # Acme user 2, travel
/tenant-globex:travel-agent:u-2001/my_memory/    # Globex
/tenant-initech:shopping-agent:u-3001/my_memory/ # Initech
/tenant-initech:shopping-agent:u-3002/my_memory/

1. Prerequisites

  • An AWS account with Amazon Bedrock AgentCore enabled in your Region (examples use eu-central-1).
  • An Amazon Cognito user pool you own (needed to control the custom:tenantId attribute).
  • AgentCore Runtime for each agent with its own execution role.
  • AWS SDK (examples use Node.js + @aws-sdk/client-bedrock-agentcore and fromTemporaryCredentials).
  • Permissions to create IAM roles/policies and Lambda functions.

2. Step 1 — Decide isolation boundaries

We need all three dimensions: tenant data must not leak, the two agents must not read each other's memories, and users must stay private. So the composite is the full three-part key:

actorId = "{tenantId}:{agentId}:{userId}"
If you only needed tenant+agent isolation (shared user memory within a tenant-agent), you'd drop userId: actorId = "{tenantId}:{agentId}". The policy and tags follow whatever composite you choose.

3. Step 2 — Create the shared memory resource

One memory resource backs every tenant. Configure retention and (for sensitive tenant data) a customer-managed KMS key. The namespace template references the composite actorId.

import boto3, time
client = boto3.client("bedrock-agentcore", region_name="eu-central-1")

resp = client.create_memory(
    name="my_memory",
    description="Shared multi-tenant memory",
    eventExpiryDuration=90,                 # raw events retained 90 days (max 365)
    encryptionKeyArn="arn:aws:kms:eu-central-1:123456789012:key/<id>",  # CMK for sensitive tenants
    memoryStrategies=[
        {"userPreferenceMemoryStrategy": {
            "name": "prefs",
            "namespaceTemplate": ["/{actorId}/my_memory/"]}},
    ],
)
memory_id = resp["memoryId"]
The {actorId} placeholder is resolved at event time from the actor you pass in. Because we scope the credentials by actorId, the resolved namespace always lands inside the caller's isolation boundary.

4. Step 3 — Author the single shared ABAC policy

Create one managed policy, MemoryNamespaceAbacPolicy. Two statements: event actions keyed on actorId, retrieval actions keyed on namespace. Both read tenantId/agentId/userId from the principal's session tags.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "bedrock-agentcore:CreateEvent", "bedrock-agentcore:GetEvent",
        "bedrock-agentcore:ListEvents",  "bedrock-agentcore:DeleteEvent"
      ],
      "Resource": "arn:aws:bedrock-agentcore:eu-central-1:123456789012:memory/my_memory",
      "Condition": { "StringLike": {
        "bedrock-agentcore:actorId":
          "${aws:PrincipalTag/tenantId}:${aws:PrincipalTag/agentId}:${aws:PrincipalTag/userId}"
      }}
    },
    {
      "Effect": "Allow",
      "Action": [
        "bedrock-agentcore:RetrieveMemoryRecords", "bedrock-agentcore:ListMemoryRecords"
      ],
      "Resource": "arn:aws:bedrock-agentcore:eu-central-1:123456789012:memory/my_memory",
      "Condition": { "StringLike": {
        "bedrock-agentcore:namespace":
          "/${aws:PrincipalTag/tenantId}:${aws:PrincipalTag/agentId}:${aws:PrincipalTag/userId}/*"
      }}
    }
  ]
}
This one policy serves all three tenants and both agents. Adding tenant-waystar tomorrow requires zero IAM changes.

5. Step 4 — Create a per-agent role with a scoped trust policy

Create two roles — TravelAgentMemoryRole and ShoppingAgentMemoryRole — and attach the shared MemoryNamespaceAbacPolicy to both. The difference is the trust policy, which pins the AgentId. Here's the shopping agent's:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::123456789012:role/ShoppingAgentExecutionRole" },
    "Action": [ "sts:AssumeRole", "sts:TagSession" ],
    "Condition": {
      "StringEquals": { "aws:RequestTag/AgentId": "shopping-agent" },
      "StringLike":   { "aws:RequestTag/TenantId": "?*",
                           "aws:RequestTag/UserId":   "?*" }
    }
  }]
}

The travel agent's role is identical but pins "aws:RequestTag/AgentId": "travel-agent" and trusts TravelAgentExecutionRole. Because agentId is fixed in trust, the shopping agent cannot assume the travel role even if misconfigured.

6. Step 5 — Configure Cognito + pre-token-generation Lambda

a
Add a custom attribute custom:tenantId to the user pool and set it per user (e.g. tenant-acme for u-1001).
b
Attach a pre-token-generation Lambda so the tenantId claim lands in the access token (custom attributes are excluded by default).
export const handler: PreTokenGenerationV2TriggerHandler = async (event) => {
  const tenantId = event.request.userAttributes['custom:tenantId'];
  if (!tenantId) throw new Error('User is missing custom:tenantId attribute');
  event.response.claimsAndScopeOverrideDetails = {
    accessTokenGeneration: { claimsToAddOrOverride: { tenantId } },
  };
  return event;
};
userId comes from the token's sub — Cognito's immutable user id — so you don't store a second identifier.

7. Step 6 — At runtime: assume the role & build a scoped client

The agent extracts tenantId (claim) and userId (sub), takes its own AGENT_ID from an environment variable, and assumes the per-agent role passing all three as transitive session tags. The returned credentials are scoped to exactly one namespace.

import { BedrockAgentCoreClient } from '@aws-sdk/client-bedrock-agentcore';
import { fromTemporaryCredentials } from '@aws-sdk/credential-providers';

// AGENT_ID supplied as an env var at deployment, e.g. "shopping-agent"
const AGENT_ID  = process.env.AGENT_ID;
const ROLE_ARN  = process.env.TVM_ROLE_ARN;   // the per-agent memory role
const REGION    = 'eu-central-1';

// tenantId from the validated token claim; userId from sub
function buildMemoryClient(tenantId, userId) {
  return new BedrockAgentCoreClient({
    region: REGION,
    credentials: fromTemporaryCredentials({
      params: {
        RoleArn: ROLE_ARN,
        RoleSessionName: `tenant-${tenantId.replace(/[^\w+=,.@-]/g,'_').substring(0,50)}`,
        Tags: [
          { Key: 'TenantId', Value: tenantId },
          { Key: 'UserId',   Value: userId },
          { Key: 'AgentId',  Value: AGENT_ID },
        ],
        TransitiveTagKeys: ['TenantId', 'UserId', 'AgentId'],
        DurationSeconds: 900,
      },
    }),
  });
}

For tenant-acme's user u-1001 on the shopping agent, the composite resolves to actorId = "tenant-acme:shopping-agent:u-1001" and the credentials can only touch /tenant-acme:shopping-agent:u-1001/my_memory/*.

Marking tags transitive makes them immutable if these credentials are used to assume another role downstream — a tenant can't be swapped mid-chain.

8. Step 7 — Store & retrieve memory through the scoped client

const actorId = `${tenantId}:${AGENT_ID}:${userId}`;  // tenant-acme:shopping-agent:u-1001
const memory  = buildMemoryClient(tenantId, userId);

// write an event (STM) — allowed only if actorId matches session tags
await memory.send(new CreateEventCommand({
  memoryId: 'my_memory', actorId, sessionId,
  eventTimestamp: Date.now(),
  payload: [{ conversational: { role: 'USER', content: { text: 'I prefer aisle seats' } } }],
}));

// retrieve long-term records (LTM) — namespace condition enforced by IAM
const recs = await memory.send(new RetrieveMemoryRecordsCommand({
  memoryId: 'my_memory',
  namespace: `/${actorId}/my_memory/`,
  searchCriteria: { searchQuery: 'seat preference', topK: 5 },
}));
// Hydrate the agent context with recs BEFORE it reasons (retrieve → reason → store).
Long-term extraction/consolidation is asynchronous (~20–40s). Use ListEvents for immediate recall within a session; RetrieveMemoryRecords for cross-session knowledge once it's consolidated.

9. Step 8 — Caching & token refresh

The ~50–200 ms AssumeRole cost shouldn't hit every request. Cache one BedrockAgentCoreClient per actorId; the SDK's assume-role credential provider auto-renews near expiry.

const clientCache = new Map();   // key = actorId (same format as namespace)

function getClient(tenantId, userId) {
  const key = `${tenantId}:${AGENT_ID}:${userId}`;
  if (!clientCache.has(key)) clientCache.set(key, buildMemoryClient(tenantId, userId));
  return clientCache.get(key);   // SDK refreshes creds at ~75% of lifetime
}
  • Derive the cache key from the validated token (already checked by AgentCore inbound auth).
  • Enable SDK retry behaviour to ride out STS throttling (default quota ~600 req/s per Region/account).
  • Use a Regional STS endpoint — quotas are per Region.

10. Step 9 — Verify isolation (make it part of deployment)

Prove the boundary with negative tests. Each should return AccessDenied, not data:

#TestExpected
1acme:shopping:u-1001 reads /tenant-globex:travel-agent:u-2001/my_memory/*Denied (tenant + agent mismatch)
2acme:travel:u-1001 reads /tenant-acme:shopping-agent:u-1001/my_memory/*Denied (agent mismatch, same tenant+user)
3acme:shopping:u-1001 reads /tenant-acme:shopping-agent:u-1002/my_memory/*Denied (user mismatch)
4Assume ShoppingAgentMemoryRole with AgentId=travel-agentDenied by trust policy
5Assume role with no TenantId/UserId tagDenied (StringLike ?* fails)
6acme:shopping:u-1001 reads its own /tenant-acme:shopping-agent:u-1001/my_memory/*Allowed ✓
Run these as an automated suite in the deploy pipeline, and watch AssumeRole denials in CloudTrail in production.

11. Troubleshooting common errors

ErrorLikely causeFix
StringLike condition not matchingRequested namespace/actorId ≠ session tagsConfirm composite order tenant:agent:user matches the policy and the namespace passed to the API.
AssumeRole access deniedTrust policy rejected the assumeCheck execution-role principal, AgentId StringEquals, and that Tenant/User tags are present.
Missing session tagsTags not passed (or not transitive)Pass all three tags and list them in TransitiveTagKeys.
STS throttling> ~600 req/s or no cachingCache clients per actorId; enable SDK retries; Regional endpoint.
Never log temporary credentials. Keep them in memory and discard after use; log only non-sensitive identifiers.

Production go-live checklist

  • Composite actorId order fixed and identical across policy, trust, and runtime
  • Single shared ABAC policy attached to every per-agent role
  • Per-agent trust policies pin AgentId; Tenant/User required via StringLike ?*
  • Namespace role separate from execution role
  • Cognito owns custom:tenantId; pre-token Lambda deployed; sub = userId
  • Transitive session tags; DurationSeconds set; Regional STS endpoint
  • Client cache keyed by actorId; auto-refresh verified
  • Negative isolation tests green in CI; CloudTrail alarms on AssumeRole denials
  • No credential logging anywhere in the path

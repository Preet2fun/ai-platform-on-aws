Multi-Tenant Agent Memory Architecture

A production-grade design for securely sharing a single Amazon Bedrock AgentCore Memory namespace across many tenants, agents, and users — using Attribute-Based Access Control (ABAC) and a single IAM policy instead of one policy per tenant.

1. Problem & motivation

AgentCore Memory gives agents short-term working memory and long-term, cross-session memory. In a multi-tenant SaaS product, many customers (tenants), several agents, and many end users all share the platform. The naive approach — a dedicated namespace and a dedicated IAM policy per tenant-agent combination — is secure but does not scale: policy count and onboarding time grow linearly with the customer base, turning minutes of onboarding into hours and inflating operational cost by orders of magnitude.

Design goal. Keep the same IAM-backed isolation guarantees as dedicated namespaces, while using one shared namespace and one shared IAM policy whose cost stays constant as tenants scale from 10 → 100 → 1,000. Reference: Secure shared multi-tenant agent memory namespaces using AgentCore Memory (AWS Builder Center).

2. Isolation model — three dimensions, defense in depth

A shared namespace still requires hard isolation so one tenant's memories never leak to another. The design enforces three independent dimensions. Taking two example agents (a travel agent and a shopping agent) serving many tenants:

Tenant isolation

Tenant A's data is never visible to Tenant B. Boundary key: tenantId.

Agent isolation

The shopping agent cannot read memories written by the travel agent — even for the same tenant. Boundary key: agentId.

User isolation

User 1's memories stay separate from User 2's within a tenant, for privacy/regulatory compliance. Boundary key: userId.

Defense in depth. Application code can enforce these boundaries, but enforcing them in IAM means AWS rejects an unauthorized request before it ever reaches your code. The IAM layer is the authoritative control; app-level checks are a second line.

3. Composite actorId & namespace layout

AgentCore Memory organizes long-term memory under a customizable namespace path that can reference pre-defined variables — actorId, memoryStrategyId, and sessionId — which are also usable as IAM policy condition keys. The key design move is to make actorId a composite of the three isolation dimensions:

actorId   = "{tenantId}:{agentId}:{userId}"

# when tenant-beta's user f36458b2 uses the travel agent:
actorId   = "tenant-beta:travel-agent:f36458b2"
namespace = "/tenant-beta:travel-agent:f36458b2/my_memory/"

Because the isolation attributes are embedded in both the actorId (used for events) and the namespace (used for retrieval), a single IAM policy can gate every dimension with ABAC condition keys sourced from session tags.

Memory action groupActionsIAM condition key
Write / read events (STM) CreateEvent, GetEvent, ListEvents, DeleteEvent bedrock-agentcore:actorId
Retrieve long-term records (LTM) RetrieveMemoryRecords, ListMemoryRecords bedrock-agentcore:namespace

The two groups support different condition keys, so the policy needs two separate statements (see §6).

4. Reference architecture

The seven-step design mirrors the AWS reference. The identity provider is the trusted source of tenant context; STS mints short-lived, attribute-scoped credentials; AgentCore Memory enforces the namespace boundary.

5. End-to-end authentication & access flow

  1. 1User authenticates against Amazon Cognito (the identity provider).
  2. 2Cognito calls a pre-token-generation Lambda that adds the tenantId claim to the access token.
  3. 3User invokes the agent runtime, passing the token as proof of authentication.
  4. 4The agent extracts tenantId from the claim and userId from sub (Cognito's immutable user id).
  5. 5The agent calls STS AssumeRole on a per-agent role, passing tenantId, agentId, userId as session tags. agentId is pinned by the role's trust policy; tenant/user arrive as tags.
  6. 6The returned temporary credentials are scoped: the composite actorId resolves to this user's namespace key.
  7. 7The agent reads/writes memory with the scoped credentials; IAM enforces the namespace boundary.

6. IAM policy design (one shared ABAC policy)

Instead of per-tenant policies, a single policy uses ABAC condition keys driven by aws:PrincipalTag values. Two statements are required because event actions and retrieval actions expose different condition keys.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      // event actions keyed on composite actorId
      "Effect": "Allow",
      "Action": [
        "bedrock-agentcore:CreateEvent",
        "bedrock-agentcore:GetEvent",
        "bedrock-agentcore:ListEvents",
        "bedrock-agentcore:DeleteEvent"
      ],
      "Resource": "arn:aws:bedrock-agentcore:<region>:<account>:memory/my_memory",
      "Condition": { "StringLike": {
        "bedrock-agentcore:actorId":
          "${aws:PrincipalTag/tenantId}:${aws:PrincipalTag/agentId}:${aws:PrincipalTag/userId}"
      }}
    },
    {
      // retrieval actions keyed on namespace prefix
      "Effect": "Allow",
      "Action": [
        "bedrock-agentcore:RetrieveMemoryRecords",
        "bedrock-agentcore:ListMemoryRecords"
      ],
      "Resource": "arn:aws:bedrock-agentcore:<region>:<account>:memory/my_memory",
      "Condition": { "StringLike": {
        "bedrock-agentcore:namespace":
          "/${aws:PrincipalTag/tenantId}:${aws:PrincipalTag/agentId}:${aws:PrincipalTag/userId}/*"
      }}
    }
  ]
}
The same policy is attached to the per-agent role of every agent that needs the namespace. Adding a tenant adds no policy; onboarding becomes constant-cost.

7. Per-agent roles & trust policies

Each agent gets its own role carrying the shared namespace policy. The role's trust policy delivers agent isolation: it allows only the agent's execution role to assume it, requires the expected session tags, and pins AgentId with StringEquals so one agent can never assume another's role — even if they share an execution role.

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::<account>:role/MyAgentExecutionRole" },
    "Action": [ "sts:AssumeRole", "sts:TagSession" ],
    "Condition": {
      "StringEquals": { "aws:RequestTag/AgentId": "shopping-agent" },
      "StringLike":   { "aws:RequestTag/TenantId": "?*",
                           "aws:RequestTag/UserId": "?*" }
    }
  }]
}

Execution role vs namespace role

The agent runs under a least-privilege execution role. The namespace role (with the ABAC policy) is separate and assumed at runtime — the execution role never holds broad memory access.

Why pin agentId in trust

If agentId is supplied as an env var at deploy and is changed accidentally, the trust policy's StringEquals blocks the assume — impersonation is structurally prevented, not merely discouraged.

8. Identity provider as the trusted source

Because isolation attributes drive IAM decisions, their source at runtime must be trusted — owned infrastructure-as-code or a validated auth token. You must own the IdP to control custom attributes such as tenantId.

  • userId ← sub. Cognito (and most IdPs) use sub as an immutable unique user id — a durable substitute for userId that never changes in a user's lifetime.
  • tenantId via pre-token generation. Custom attributes aren't in access tokens by default; a Cognito pre-token-generation Lambda copies custom:tenantId into the token claims so the runtime can read it.
export const handler = async (event) => {
  const tenantId = event.request.userAttributes['custom:tenantId'];
  if (!tenantId) throw new Error('User is missing custom:tenantId');
  event.response.claimsAndScopeOverrideDetails = {
    accessTokenGeneration: { claimsToAddOrOverride: { tenantId } },
  };
  return event;
};

9. Performance, caching & resilience

Latency

STS AssumeRole adds ~50–200 ms depending on configuration. Acceptable for many use cases; mitigate with caching.

Token lifecycle

Refresh credentials for long-running sessions at ~75% of the token lifetime.

Throttling

STS default quota is ~600 req/s per Region per account, shared across several operations including AssumeRole.

Cache key

Use the same format as the actorId. Derive it from the validated token (already checked by AgentCore inbound auth).

  • Cache BedrockAgentCoreClient instances, each scoped to the correct actorId; let the SDK's assume-role credential provider refresh automatically.
  • Use SDK retry behaviours to absorb throttling; use a Regional STS endpoint (quotas are per Region).
  • Monitor AssumeRole access violations in CloudTrail; run end-to-end isolation tests in the deployment pipeline. Common errors: StringLike condition not matching, AssumeRole access denied, missing session tags.
Never log temporary credentials. Keep them in memory only and discard after use.

10. The design through the six Well-Architected pillars

PillarHow this design addresses it
SecurityIAM is the authoritative boundary (defense in depth); three isolation dimensions in the composite actorId; agentId pinned in trust policy; transitive/immutable session tags; trusted IdP; credentials never logged; encryption at rest/in transit and optional CMK inherited from the memory resource.
ReliabilitySDK retry + assume-role credential provider for auto-refresh; Regional STS endpoint; graceful handling of throttling; end-to-end isolation tests gate deployment. LTM extraction remains asynchronous — design for the ingest→availability delay.
Operational ExcellenceOne policy and one namespace to operate; onboarding a tenant requires no new IAM; CloudTrail monitoring of AssumeRole and quota dashboards; IaC-managed roles and attributes.
PerformanceCache scoped clients to amortize the ~50–200 ms AssumeRole cost; semantic retrieval ~200 ms; parallel strategy processing unaffected by the isolation layer.
CostConstant IAM/management cost as tenants scale (no policy multiplication); shared namespace avoids per-tenant resource sprawl; attach only needed strategies.
SustainabilityFewer provisioned IAM artifacts and resources per tenant; shared infrastructure and bounded retention reduce footprint.

11. Design checklist (acceptance)

  • ☐ Isolation boundaries decided (tenant? agent? user?) and encoded as the composite actorId
  • ☐ Single shared ABAC policy with two statements (actorId for events, namespace for retrieval)
  • ☐ Per-agent role per agent; trust policy pins AgentId (StringEquals) and requires Tenant/User tags (StringLike)
  • ☐ Namespace role separate from the agent execution role (least privilege)
  • ☐ IdP owned; sub → userId; pre-token Lambda injects custom:tenantId
  • ☐ Session tags marked transitive (immutable on downstream AssumeRole)
  • ☐ Caching keyed on actorId; credential auto-refresh at ~75% lifetime; Regional STS endpoint
  • ☐ CloudTrail monitoring + end-to-end isolation tests in the pipeline; credentials never logged

12. Trade-offs & alternatives

DimensionDedicated namespace + policy per tenantShared namespace + ABAC (this design)
IAM policy countGrows linearly with tenantsConstant (one shared policy)
Onboarding timeMinutes → hours at scaleNear-instant (no provisioning)
Isolation strengthIAM-backedIAM-backed (equivalent)
Runtime latencyNo per-request AssumeRole+~50–200 ms (mitigated by caching)
Best fitFew, static tenantsLarge, dynamic tenant base that must scale

Choose dedicated namespaces only for a small, static tenant set. For any application intended to scale to a large, dynamic number of tenants/agents, the shared-namespace ABAC pattern is the production default.
